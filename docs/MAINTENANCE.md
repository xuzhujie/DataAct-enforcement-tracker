# Data Act tracker maintenance

## What the dashboard distinguishes

- **Complaint route** is the public form or channel for a person or company to contact the competent authority. It is not evidence that a complaint was filed or that an authority opened a case.
- Complaint routes can be filtered by scope: **general Data Act / non-personal-data intake** versus the **Article 37(3) personal-data boundary**. The scope label does not upgrade a draft route to a final legal procedure; use the route’s own `verified` / `pending` status for that distinction.
- **Statutory penalty cap** is the maximum sanction supported by the applicable domestic law or official implementation text. It is not an amount imposed in a real case.
- **Actual public penalty** is populated only from an official decision, register entry, or official announcement that can be traced to a specific Data Act matter. An empty case register means that no publicly traceable decision was located in the reviewed official sources; it does not mean that no investigation exists.

The current registry snapshot is dated `2026-11-21`. It covers all 27 EU Member States, with 5 deep-verified records, 22 partial records, and no country hidden behind an invented zero or a synthetic enforcement case.

The field-level view is intentionally more granular than the coverage label: 17 country records have a verified authority field for at least the Data Act personal-data boundary and 10 have an officially signalled but still pending general authority; all 27 now expose a public complaint route, with 20 records at verified status and 7 records still pending because they combine a verified Article 37(3) data-protection route with a draft or unconfirmed general Data Act procedure; 6 have a verified domestic penalty schedule and 9 have proposed ceilings recorded as pending, while 12 remain not located; and the official Data Act case register currently contains 0 cases. A verified personal-data authority or complaint route is not treated as proof of a complete national Data Coordinator designation or a general Article 38 route for non-personal-data obligations. The remaining fields are displayed as `pending` or `not_located`, not as zero.

## Local checks

```bash
npm test
npm run lint
npm run build
npm run validate:registry
npm run check:sources -- --output source-health.json
npm run compare:sources -- --previous .monitor/source-health-baseline.json --current source-health.json --output source-changes.json
npm run report:maintenance -- --source-health source-health.json --output maintenance-report.json
```

`validate:registry` is deterministic and checks the EU-27 shape, source metadata, nested evidence references, issue lenses, implementation metadata, and case/source integrity. `check:sources` fetches each unique official URL twice at most, follows redirects, and writes a machine-readable report. It records a SHA-256 fingerprint of up to the first 64 KiB of each response so that a page or document update can be triaged without downloading unbounded content. It intentionally fails on network errors and non-2xx/3xx responses; a 403 or anti-bot response is a maintenance signal, not permission to silently downgrade or overwrite verified data. `compare:sources` compares the current report with a prior report and classifies added, removed, content-changed, failed, and recovered sources; the first run has no baseline and therefore emits no change alert.

`report:maintenance` builds a second machine-readable artifact: it summarizes coverage, field-level evidence gaps, actual case count, due review items, and any source-health failures. Its `asOf` value defaults to the current UTC date for review scheduling; use `--as-of YYYY-MM-DD` to reproduce a historical report. This review date is separate from the registry evidence snapshot date. The command is a reporting step only; it never writes legal facts back into the registry.

For human intake, `.github/ISSUE_TEMPLATE/data-act-evidence-refresh.yml` provides a structured evidence-refresh form. It requires a country, affected field, evidence status, official source URL(s), factual summary, verification date, and confirmation that the source is primary. The form is an intake mechanism only; a maintainer still reviews the source and changes the registry manually.

## Weekly monitoring

`.github/workflows/data-act-source-monitor.yml` runs every Monday at 02:00 UTC and can also be started with `workflow_dispatch`. It validates the registry, checks all unique source URLs, compares response fingerprints against the prior run’s cached baseline, builds `maintenance-report.json`, and uploads the source-health, source-change, and maintenance reports as artifacts. A failed source check creates or comments on the open issue `Data Act source check failed`; a detected content change or availability transition creates or comments on `Data Act official source changed or recovered`; a due review queue creates or comments on `Data Act tracker maintenance review due`. The workflow does not mutate the registry or publish unverified facts; each alert still requires a human review of the primary source.

## Update protocol

1. Start from the country record and its source manifest; do not replace an official source with a search-result URL.
2. Record the field-level status (`verified`, `pending`, `not_located`, or `not_applicable`) and `lastVerifiedAt` for every change.
3. Keep complaint routes, statutory penalty caps, and actual public penalties in separate fields.
4. Add a case only when an official decision or official authority announcement identifies the Data Act matter, and register the supporting source as `official-decision`; keep the case register empty when no such record is found.
5. Run the local checks, review the source-health failures, and update the maintenance queue rather than filling gaps with zero values.
